1 — Engineering Ownership · Session 03

Validation Before Trust

🚧 DRAFT 🚧

Turn plausible output into evidence-backed output by choosing validation methods that match the artifact and its risk.

Estimated time: 45–60 minutes · Initial implementation; validation is still pending.

1. Learning Objectives

  • Distinguish review from validation.
  • Build a validation ladder from cheap checks to realistic evidence.
  • Match validation to C#, Python, UI, SQL, and infrastructure artifacts.
  • Stop when evidence is proportionate—not merely when a tool reports success.

2. Before You Begin

Write a one-sentence answer before continuing:

If AI produced a change that passed a quick check, what would you still need to own?

3. The Concept

1. Review asks; validation demonstrates

Review identifies questions and risks. Validation gathers evidence through parsing, builds, tests, static analysis, dry runs, plans, deployments to safe environments, and observation.

2. Use a validation ladder

Start with fast deterministic checks, then move toward integration and production-like evidence as consequence increases. Passing a lower rung does not imply a higher rung will pass.

3. Validate the artifact in context

A Terraform plan can be syntactically valid and still replace a database. A unit test can pass while the UI remains inaccessible. Evidence must address the actual consequence.

4. Record limits

Every validation result has a boundary: environment, data, permissions, configuration, and time. State what was not demonstrated so confidence is not overstated.

Working rule: AI output is a candidate artifact. Confidence comes from engineering evidence, not fluency or speed.

4. Lab

Exercise

Design validation ladders for one application change and one infrastructure change. Include the command or observation at each rung, the risk it addresses, the expected result, and the stop/escalation condition. Execute only safe checks available in your environment and record their limits.

5. Expected Evidence

  • Two validation ladders
  • Results from safe executable checks
  • Explicit unvalidated risks
  • A go, revise, or escalate recommendation

  • Which validation rung changed your confidence most?
  • What important behavior remains unproven?
  • When would you require another engineer or environment?
